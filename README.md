# cascad_oc

Решение каскадных систем ДУЧП + ОДУ для задач оптимального управления.

Текущая архитектура (точки, переменные, блоки-композиция, `System.solve()`,
границы как ОДУ) описана в [`src/cascadoc_new/README.md`](src/cascadoc_new/README.md).
Демонстрация трёх этапов граничной логики — в
[`example/cascadoc_new_blocks.ipynb`](example/cascadoc_new_blocks.ipynb).

---

## Задача на следующий шаг: функции, неизвестные заранее

### Чего хочется

Сейчас **все функции задачи известны до решения**: коэффициенты `B, F`,
граничные `G`, начальные `x0/y0`, терминальные `phi_*` регистрируются заранее
как `AnalyticVariable`/`var_callable` (`build_hyp_blocks`), а блоки только
потребляют их. Граница может задаваться ОДУ (`ODEBlock`), но сам ОДУ задан
известными коэффициентами `G`.

Хочется, чтобы систему можно было собирать по принципу:

> Есть гипотетическая система, у которой границы (и/или правые части) заданы
> **функциями**, и эти функции **не известны заранее**. Но их **можно вычислить
> на определённом шаге**, решив ОДУ. Аналогично — для любой другой функции:
> например, одна из правых частей гиперболической системы заранее неизвестна и
> **сама является решением ОДУ**; в процессе решения её считают, и дальше она уже
> известна.

То есть функция перестаёт быть «входным данным» и становится **величиной,
разрешаемой в ходе решения** — ровно как `X` или `PSI`. Потребитель (например
`HypBlock` или граничный блок) должен получать её значение лениво, на том слое
`t`, где оно уже посчитано.

### Что нужно сделать

1. **Ввести «отложенную» функцию.** Новый вид переменной/ссылки (условно
   `DeferredVariable` / `ResolvedFunction`): объявляется по имени и
   размерности, но без формулы. Значение `at(point)` берётся из результата уже
   посчитанного блока, а не из `lambda`.

2. **Связать функцию с блоком-источником.** Указать, какой блок её производит
   (например, отдельный `ODEBlock`, решающий `df/dt = ...` на своих слоях) и в
   какой `NumericVariable` он пишет результат.

3. **Разрешать функцию лениво по слою.** `System.solve()` уже идёт послойно по
   `t`. Гарантировать, что на каждом слое сначала считаются функции/блоки-
   источники, а затем их потребители. Порядок блоков внутри слоя сейчас
   «не важен» (см. `System.solve`) — это допущение придётся ослабить: ввести
   упорядочивание блоков/зависимостей, чтобы источник шёл раньше потребителя.

4. **Дать потребителю доступ к функции.** `HypBlock` и `boundary_ode_step`
   читают коэффициенты через `_coef(system, 'F1', point)`. Нужно, чтобы такое
   чтение возвращало значение отложенной функции из посчитанного хранилища
   (или `None`/ошибку, если слой ещё не готов — как индикатор неверного
   порядка).

### Пример-эталон (критерий приёмки)

Взять задачу из `example/cascadoc_new_blocks.ipynb` (`x = exp(s + c1·t)`,
`y = exp(-s + c2·t)`) и модифицировать так:

* одна из правых частей (например `F1(s, t)` или `F2(s, t)`) **не задана
  формулой**, а является решением собственного ОДУ, которое подобрано так,
  что его решение совпадает с прежним `F`;
* эта «неизвестная» функция регистрируется как отложенная и производится
  вспомогательным блоком;
* `HypBlock` использует её в правой части.

Проверка: решение должно **совпасть с эталоном**, где та же функция задана
аналитически (норма разности `max|Δ|` в пределах порядка схемы; при точном
подборе ОДУ — вплоть до побитового совпадения, как `HypBlock + ODEBlock` против
`TrapezoidalSolver` в текущем ноутбуке).

### Критерий готовности

* Можно собрать систему, где хотя бы одна функция задачи неизвестна заранее и
  разрешается в ходе решения через ОДУ.
* Порядок разрешения функций детерминирован и не зависит от порядка
  `add_block` (зависимости блоков/функций явные).
* Результат совпадает с эталоном, где функция задана аналитически.
* Тесты: unit-тесты на разрешение функции по слою + сверка с аналитикой;
  при переданном ОДУ с точным решением — совпадение с монолитным решателем.
